## 性能原因与实测

主要确认的瓶颈是 WM eager 执行的 CPU kernel 提交开销。单次更新 profiler 记录 11,383 次 `cudaLaunchKernel`；启用 graph 后为 144 次普通启动加 1 次 `cudaGraphLaunch`。这与 [PyTorch CUDA Graph 文档](https://docs.pytorch.org/docs/main/notes/cuda.html#cuda-graphs) 描述的减少 CPU 启动开销机制一致。Profiler 单独运行，不计入测速。

同一生产检查点、同一真实 batch、恢复相同优化器与 RNG 状态，对照结果：

| 项目 | 优化前 | 优化后 |
| --- | ---: | ---: |
| WM 单次更新中位数（5 次） | 70.78 ms | 30.23 ms |
| 实际训练网络更新/轮中位数 | 0.802 s | 0.408 s |
| 实际采集+更新/轮中位数 | 0.930 s | 0.512 s |

受控 WM 对照加速 2.34 倍，首末更新的全部指标相等。实际训练核心循环吞吐约提高 1.81 倍；不包含所有录像、审计、保存开销。实际前后比较使用优化前最后 100 轮和续训剔除前 5 轮的数据，因重启重建仿真/replay、轨迹不同，不是完全受控的端到端比较。

优化后 34 次一秒间隔 GPU 利用率抽样中位数 84%，范围 54–97%。这只代表该抽样窗口，不保证持续满载。保持 1024 环境、现有 batch、FP32 和优化器设置；Actor microbatch 4096 对照比 2048 更快，因此保留 4096。
